# 단계 1 결과: F1 (Framework) · H1 (Harness)

실행: 2026-10-28. 모델: OpenRouter `anthropic/claude-opus-5.5`. 후보마다 3회 반복. 개발 실행을 포함한 총비용은 약 $2.1이다.
원자료: [summary-f1-final.md](../results/summary-f1-final.md), [summary-h1-final.md](../results/summary-h1-final.md), `results/runs/*/result.json`, `results/proxy/calls.jsonl`.

## 결론

- **Framework**: 도구 호출과 구조화 출력만 쓰는 단순 과제에서는 7개 모두 성공했다. 토큰, 시간, 비용 차이는 10% 안팎이었다. 실제 차이는 결과가 아니라 만드는 방식에서 났다. 코드와 의존성 크기, 구조화 출력의 구현 방식, 최신 모델과의 호환성이다.
- **Harness**: 4개 모두 버그 수정 과제를 3번 모두 풀었다. 과제가 쉬워 성공률로는 구분되지 않았다. 차이는 하네스가 기본으로 싣는 컨텍스트의 크기(첫 요청 2K~17K 토큰)와 그에 따른 비용이었다.

¹ 1회는 LLM 응답이 오지 않아 600초 타임아웃으로 실패했다(프록시 기록 0건). 따로 3회를 다시 실행했고 모두 성공했다(3/3, 중앙값 12.2초). 일시적인 업스트림 문제로 보고, 이후 프록시가 끝나지 않은 요청도 기록하게 고쳤다.
² TypeScript에는 런타임 타입 정보가 없어서 도구 스키마와 출력 스키마를 zod로 직접 선언해야 한다. 이 선언은 `shared.ts`(37줄)로 분리했다. Python 후보는 같은 정보를 타입 힌트, docstring, Pydantic 모델에서 자동으로 얻는다.

### 관찰

1. **실행 결과의 차이는 작다.** 거의 모든 실행이 같은 흐름으로 LLM을 3번 호출했다. 첫 호출에서 도구 3개를 병렬로 부르고, 두 번째 호출에서 이슈 상세 조회 2건을 병렬로 부른 뒤, 세 번째 호출에서 답을 냈다. 비용은 $0.042~0.047, 시간은 10.5~13.1초였다.
2. **프레임워크가 프롬프트에 끼워 넣는 내용이 다르다.** 첫 요청의 입력 토큰은 Strands가 1,638로 가장 적고 CrewAI가 2,113으로 가장 많았다(+29%). CrewAI는 role, goal, backstory로 시스템 프롬프트를 만들고 과제 설명을 자체 형식으로 감싼다. 사용자 메시지 길이가 2,279자로, 다른 후보의 408자보다 훨씬 길었다. ADK는 "You are an agent. Your internal name is …" 문장과 `set_model_response` 도구 사용 지시를 덧붙인다.
3. **구조화 출력 구현 방식이 세 갈래로 나뉘고, 최신 모델과의 호환성이 갈렸다.**

   | 방식 | 후보 |
   | --- | --- |
   | 모델에 JSON schema 응답을 요청 (`response_format`) | OpenAI Agents SDK, Mastra (기본값), LangGraph, Pydantic AI (설정 변경 후) |
   | 출력용 도구를 추가하되 호출을 강제하지 않음 | Strands (기본값), ADK (`set_model_response`) |
   | 최종 텍스트를 파싱 | CrewAI |
   | 출력용 도구 호출을 강제 (`tool_choice: any`) → **Opus 5.5가 400으로 거부** | LangGraph 기본값 (`ToolStrategy`), Pydantic AI 기본값 (도구 출력) |

4. **설치 크기는 13배 차이가 난다.** Pydantic AI(slim)는 패키지 26개에 56MB, CrewAI는 137개에 732MB였다. CrewAI는 도구 하나짜리 에이전트에도 Kubernetes 클라이언트, 벡터 DB, ONNX 런타임 같은 의존성을 함께 설치한다.
5. **코드량은 대부분 12~16줄이다.** ADK만 27줄인데, Runner와 Session을 만들고 이벤트 스트림에서 최종 응답을 꺼내는 코드가 필요하기 때문이다.

| Deep Agents | 비어 있음 ³ | 9개 | 지정 안 함 (API 기본값) | 4,540 | $0.067 |

³ Deep Agents는 0.7.0부터 기본 시스템 프롬프트를 없앴다. 대신 모델별 프로필이 접미사를 붙이는데, 0.7.32에는 Opus 4.7, Sonnet 4.6, Haiku 4.5용 프로필만 있어서 Opus 5.5에서는 빈 시스템 프롬프트로 동작한다. 지침은 도구 설명에 담겨 있다.

### 관찰

1. **과제는 모두 쉽게 풀었다.** 모든 하네스가 LLM 호출 4번, 15~20초 만에 끝냈다. 다른 버그를 고쳐야 드러나는 실패를 하나 숨겨 두었지만 모두 처리했다. 천장 효과가 있어서 성공률로는 하네스를 구분할 수 없었다.
2. **차이는 기본 오버헤드에서 난다.** Claude Agent SDK는 첫 요청부터 17K 토큰을 보낸다(시스템 프롬프트와 도구 12개). Pi의 6.5배, Flue의 8.5배다. 캐시가 데워진 반복 실행에서는 Pi와의 비용 차이가 2.3배($0.061 대 $0.027)로 줄지만, 캐시가 빈 첫 실행에서는 3.3배($0.150 대 $0.046)다.
3. **네 하네스 모두 Anthropic 프롬프트 캐시를 쓴다.** 입력 토큰 중 캐시 읽기 비율은 Deep Agents 98.3%, Pi 97.5%, Claude Agent SDK 95.7%, Flue 77.8%였다. Flue는 입력 토큰이 가장 적었지만 캐시 적중률이 낮아 비용은 두 번째로 높았다.
4. **설정이 완전히 같지는 않다.** Deep Agents만 effort를 보내지 않아 API 기본값으로 동작했고, 나머지 셋은 `high`였다. 이번 과제에서는 결과 차이가 없었지만, 어려운 과제에서는 통제해야 한다.

## DX 메모: 막힌 지점과 해결

| 후보 | 막힌 지점 | 해결 |
| --- | --- | --- |
| LangGraph | `response_format` 기본값이 강제 `tool_choice`를 보내 400 | `ProviderStrategy(...)`로 한 줄 변경 |
| Pydantic AI | 기본 도구 출력이 강제 `tool_choice`를 보내 400 | `NativeOutput(...)`으로 한 줄 변경 |
| Google ADK | LiteLLM 1.106.5가 도구가 있으면 선언되지 않은 `mcp` 패키지를 import해서 LLM 호출 전에 실패 | `mcp` 의존성 추가 |
| OpenAI Agents SDK | 기본값이 Responses API와 OpenAI 트레이스 전송 | `OpenAIChatCompletionsModel` 사용, `set_tracing_disabled(True)` |
| CrewAI, Strands, Mastra | 없음 | 그대로 동작 |
| Claude Agent SDK | SDK 기본 시스템 프롬프트는 Claude Code 프리셋이 아님. 보조 작업용 모델이 다른 모델로 갈 수 있음. root에서 `bypassPermissions`가 막힘 | 프리셋 명시, 모델 환경변수 4개를 같은 모델로 고정, `IS_SANDBOX=1` |
| Deep Agents | 기본 backend가 가상 파일시스템이라 실제 파일과 셸을 쓸 수 없음 | `LocalShellBackend` 지정 (격리는 컨테이너가 맡음) |
| Pi | 없음 | `models.json`에서 내장 openrouter 공급자의 `baseUrl`만 바꿈 (가장 간단) |
| Flue | `flue run`이 `app.ts`를 읽지 않아, 에이전트 모듈 안에서 공급자를 다시 등록해야 함 | 약 12줄 + `@earendil-works/pi-ai` 직접 의존성 추가 |

## 한계

- 두 과제 모두 쉬워서 성공률 차이가 나지 않았다.
- 3회 반복, 단일 모델, 각 후보의 기본 설정끼리 비교한 결과다.
- 비용은 프롬프트 캐시 상태에 따라 달라진다. 캐시 TTL이 5분이고 같은 후보를 연달아 실행했으므로, 중앙값은 대체로 캐시가 데워진 상태의 값이다.

## 다음 단계 제안

1. **설계대로 단계 2 진행**: F2(멀티에이전트)와 F3(사람 승인 후 재개)는 프레임워크마다 구현 방식이 가장 크게 갈리는 과제다. H2(데이터 분석 리포트)와 H3(커스터마이징)는 하네스의 확장성을 본다.
2. **하네스 트랙에 더 어려운 과제 추가 검토**: H1은 천장 효과가 있었다. 여러 파일에 걸친 기능 구현이나 요구사항이 모호한 수정처럼 성공률이 갈릴 만한 과제가 필요하다.
3. **effort 통일**: 하네스 비교에서 effort를 하나로 고정해 공정성을 보강한다.
